## 1. Удиртгал

Олон процесс нэг CPU-г хуваан хэрэглэх үед ready queue-д байгаа task-уудаас алийг нь, хэдий хугацаагаар ажиллуулахыг CPU scheduler шийддэг. Энэ шийдвэрээс task-ын хүлээх хугацаа, хариу өгөх хурд, context switch-ийн тоо шууд хамаарна. Ижил ачааллыг өөр алгоритмаар хуваарилахад эдгээр үзүүлэлт эрс ялгаатай гарч болно. Энэ төслөөр сурах бичгийн таван алгоритмыг хэрэгжүүлж, тэдгээрийн ялгааг Gantt chart болон тоон үзүүлэлтээр туршиж харьцуулахыг зорив [1].

Хамрах хүрээ нь нэг CPU-тэй, бүхэл тоон хугацаатай simulated (виртуал) цаг юм. Task-ууд бодитоор ажиллахгүй. `run()` функц нь цагийг урагшлуулж, ямар task хэзээ ажилласныг бүртгэдэг. Context switch-ийн зардал, I/O burst, олон CPU, preemptive SJF (SRTF), aging-ийг хэрэгжүүлээгүй. UI нь C програмын бодит гаралтыг шууд дүрсэлдэг.

## 3. Онолын үндэс

**FCFS** нь task-уудыг ирсэн дарааллаар бүтэн burst-аар ажиллуулна. **SJF** нь ирсэн task-уудаас burst хамгийн богинийг сонгоно. Бүх task зэрэг ирсэн үед SJF нь дундаж waiting time-ийг хамгийн бага болгодог нь батлагдсан [1, §5.3.2]. **Priority** нь priority хамгийн өндөр task-ыг сонгоно. Бага priority-тэй task хязгааргүй хүлээх (starvation) аюултай бөгөөд үүнийг aging-аар шийддэг. **RR** нь ready queue-гийн эхний task-ыг нэг quantum (q) хугацаагаар ажиллуулаад, дуусаагүй бол queue-гийн ард буцаана. **Priority-RR** нь priority бүрт тусдаа queue хөтөлж, хамгийн өндөр priority-тэй хоосон биш queue дотроо RR хэрэглэнэ [1, Figure 5.7]. SJF ба Priority-д тэнцсэн үед FCFS дарааллаар сонгох тул үр дүн дахин давтагдана.

Task *i*-ийн хувьд turnaround time нь TATᵢ = Finishᵢ − Arrivalᵢ, waiting time нь WTᵢ = TATᵢ − Burstᵢ, response time нь RTᵢ = Startᵢ − Arrivalᵢ байна. Энд Start нь task анх CPU авсан агшин. CPU utilization нь нийт burst-ыг сүүлийн task дууссан хугацаанд хуваасантай тэнцүү. Context switch-ийг өөр task руу шилжсэн тоогоор тоолсон бөгөөд CPU idle байсныг тооцоогүй.

Хоёр онолын хүлээлтийг туршилтаар шалгана. Эхнийх нь convoy effect: FCFS-д урт task түрүүлбэл богино task-ууд бүгд удаан хүлээнэ. Хоёр дахь нь quantum-ын нөлөө: q хамгийн урт burst-аас их бол RR нь FCFS-тэй ижил болно, q багасах тусам response time буурч context switch өснө [1, §5.3.3].

## 4. Системийн зохиомж

Оролт нь schedule файлаас эсвэл UI-аас ирнэ. `driver.c` нь мөр бүрийг шалгаад `add()`-аар тухайн алгоритмын list-д оруулна. `schedule()` нь давталтаар `pickNextTask()` → `run()` гүйцэтгэнэ. `cpu.c` нь `run()` бүрийн хугацааг timeline-д бүртгэнэ. `stats.c` нь timeline болон task-уудаас метрикийг тооцож, текстээр эсвэл `-j` сонголттой үед JSON хэлбэрээр хэвлэнэ. UI сервер нь C програмыг subprocess-оор ажиллуулж, JSON-ийг browser руу дамжуулна. UI-д тусдаа scheduling алгоритм байхгүй.

![Системийн зохиомж](docs/images/architecture.png)

*Зураг 1. Компонентууд ба өгөгдлийн урсгал*

Makefile нь нийтлэг таван файлыг (`driver`, `list`, `cpu`, `task`, `stats`) нэг `schedule_*.c`-тэй холбож, алгоритм бүрт тусдаа executable гаргана.

Өгөгдлийн бүтэц: `Task(name, tid, priority, burst, arrival, remaining, start, completion)`. FCFS, SJF, Priority нь номд санал болгосноор эрэмбэлээгүй нэг linked list ашиглаж, `pickNextTask()` бүрт list-ийг бүхэлд нь шалгана. RR нь list-ийг FIFO queue болгон `append()`, `pop_front()` ашиглана. Priority-RR нь `queue[1..10]` массивтай. Timeline нь `Segment(task, start, end)`-ийн динамик массив бөгөөд `task = NULL` нь CPU idle-ийг илэрхийлнэ.

**Timeline-ийн invariant**

- Сегментүүд 0-ээс эхэлж, хоорондоо завсаргүй, давхцалгүй үргэлжилнэ.
- Нэг task-ын сегментүүдийн нийлбэр нь яг түүний burst-тай тэнцүү.
- Task-ын анхны сегмент нь arrival-аас өмнө эхлэхгүй.
- RR-д нэг сегмент q-ээс урт байхгүй.

## 5. Хэрэгжилт

C11 (GCC 13, Clang 18) хэлээр, зөвхөн C standard library ашиглав. UI сервер нь Python standard library (`http.server`, `subprocess`), UI нь framework-гүй HTML, CSS, JavaScript (SVG) юм. Гуравдагч талын dependency байхгүй.

| Функц | Гол шийдэл | Хугацаа |
|---|---|---|
| `read_schedule()` | Мөр задлах, талбар шалгах, давхардсан нэр хайх | O(n²) |
| `pickNextTask()` | FCFS/SJF/Priority: ирсэн task-уудаас хамгийн сайныг хайх | O(n) |
| | RR: `pop_front`; Priority-RR: хамгийн өндөр хоосон биш queue | O(1) / O(10) |
| `schedule()` | Non-preemptive: n удаа сонгох | O(n²) |
| | RR: slice бүрийн дараа шинэ ирэлт оруулах, ард нэмэх | O(S·n) |
| `run()` | Цаг урагшлуулах, сегмент нэмэх, start/completion тэмдэглэх | O(1) |
| `stats_compute()` | Task бүрийн TAT, WT, RT, дундаж, utilization | O(n) |

Энд n нь task-ын тоо, S нь RR-ийн slice-ийн тоо. RR-д slice дуусахад тэр агшинд ирсэн task-ууд эхлээд queue-д орж, дараа нь preempt хийгдсэн task ард нэмэгдэнэ. Ирсэн task байхгүй үед `cpu_idle_until()` дараагийн arrival хүртэл idle сегмент үүсгэнэ.

`driver.c` нь бүх мөрийг scheduler эхлэхээс өмнө шалгадаг тул алдаатай файл хагас ажиллахгүй. Талбарын тоо (3 эсвэл 4), нэр (үсэг, тоо, `_ - .`, давхардахгүй), priority (1–10), burst (1–10⁶), arrival (0–10⁶), quantum (≥ 1) зэргийг шалгана. Таслал агуулсан мөрийг зөвхөн таслалаар хуваах тул `T 1, 4, 20` мөрийг "T" нэртэй task гэж буруу уншихгүй, алдаа гэж мэдээлнэ. RR-д 200 000-аас олон slice үүсэхээр бол санах ойг хамгаалж татгалзана.

Номын Further Challenge 1-ийн дагуу tid-ийг `__sync_fetch_and_add(&next_tid, 1)`-аар atomic байдлаар олгоно. Симулятор нэг thread-тэй тул race condition бодитоор үүсэхгүй ч олон CPU дээр scheduler тус бүр task үүсгэх нөхцөлд аюулгүй.

## 6. Туршилт ба UI дүрслэл

Хэрэглэгч алгоритм, time quantum, task-уудын нэр, priority, burst, arrival-ийг өөрчилж туршина. Task-уудыг текст талбарт schedule файлын форматаар бичих, 7 бэлэн жишээнээс сонгох, санамсаргүй үүсгэх, `.txt` файлаас ачаалах боломжтой. "Ажиллуулах" дарахад C програм ажиллаж, Gantt chart t = 0-ээс эхлэн тоглуулагдана. Тоглуулагч нь тоглуулах/зогсоох, өмнөх/дараагийн үйл явдал руу алхах, хугацааны slider, хурдтай. "Бүх алгоритмыг харьцуулах" нь ижил task-ууд дээр таван алгоритмыг нэг хугацааны тэнхлэгт харуулна. Reset нь анхны тохиргоонд буцаана.

Дээд мөр нь номынх шиг CPU-гийн Gantt chart бөгөөд блок бүрийн өргөн нь хугацаатай пропорционал. Доор нь task бүр өөрийн мөртэй: тасархай хүрээ нь ready queue-д хүлээсэн хугацаа, дүүргэлттэй блок нь ажилласан хугацаа, ▼ нь ирсэн агшин, ✓ нь дууссан агшин. Ташуу зураастай саарал блок нь CPU idle, улаан босоо шугам нь одоогийн t. "Төлөв" хэсэг нь t агшинд ажиллаж буй, ready, ирээгүй, дууссан task-уудыг харуулна. Task бүр оролтын дарааллаараа тогтмол өнгөтэй. 8-аас олон task байхад өнгө давтагдах тул 9 дэх task-аас эхлэн ташуу зураасаар ялгана. Блокууд дээр нэр бичигдэх тул өнгөөр ялгах шаардлагагүй.

## 7. Туршилтын арга

Орчин: Ubuntu 24.04 (x86-64), GCC 13.3.0, Clang 18.1.3 (`-std=c11 -Wall -Wextra -pedantic`), Python 3.13. UI-г Chromium (Playwright) дээр автоматаар ажиллуулж шалгасан. Багийн Windows + WSL (Ubuntu) орчинд `make`-ээр build хийсэн.

73 автомат тест дөрвөн хэсгээс бүрдэнэ. **Golden** (49): 5 алгоритм × 7 өгөгдлийн файл, RR-д q = 10 ба q = 4. Гаралтыг `tests/expected/`-тэй тэмдэгт бүрээр нь тулгана. **Алдаа** (13): буруу оролтын файл бүрд exit 1 ба тодорхой мессеж гарах ёстой. **Сонголт** (10): `-q 0`, `-q abc`, файлгүй, мэдэгдэхгүй сонголт, JSON-ийн зөв эсэх. **Reference** (1): `tests/reference_check.py` нь C кодыг хуулбарлаагүй, Python дээр бие даан бичсэн таван алгоритм. Seed = 1-ээр 300 санамсаргүй task set (1–12 task, 60% нь arrival-тай, q ∈ {1, 3, 4, 5, 10, 20}) үүсгэж, timeline болон task бүрийн бүх метрикийг C-ийн гаралттай тулгана.

Golden тестийн expected файлуудыг програм өөрөө үүсгэсэн тул тэд зөвхөн регрессийг илрүүлдэг. Зөв ажиллагааг номын жишээний гар тооцоо болон reference тестээр баталгаажуулав. Нэмэлтээр AddressSanitizer, UndefinedBehaviorSanitizer-тэй build дээр бүх файлыг таван алгоритмаар ажиллуулсан. UI-д 5 сценарийг (ажиллуулах, t агшинд зогсоох, харьцуулах, алдаатай оролт, dark mode дээр 12 task) автоматаар гүйцэтгэж, browser console-ийн алдааг шалгасан.

| 25 | 63.0 | 44.0 | 44.0 | 4 |
| 30 | 63.0 | 44.0 | 44.0 | 4 |

q ≥ 25 (хамгийн урт burst) үед RR-ийн үр дүн FCFS-тэй яг ижил боллоо. q = 1 үед RT 2.0 болж буурсан ч context switch 94 болж өссөн. 8 task-тай `eight.txt` дээр ч ижил хандлага ажиглагдсан: q = 30 үед RR = FCFS (94.38 / 73.13), q = 1 үед context switch 165.

### 8.5. Алдаатай оролт

`T2, 11, 25` мөр бүхий оролтыг өгөхөд програм scheduling эхлүүлэлгүйгээр `line 2: priority '11' must be an integer from 1 to 10` мессеж гаргаж, 1 кодоор гарав. UI нь энэ мессежийг хэрэглэгчид харуулж, өмнөх chart-ыг арилгана.

## 9. Хэлэлцүүлэг

Бүх task 0-д ирдэг дөрвөн өгөгдлийн багцын бүгдэд SJF хамгийн бага дундаж waiting time өгсөн нь онолтой нийцэж байна. Гэхдээ SJF нь дараагийн burst-ын уртыг урьдчилан мэдэх шаардлагатай. Энэ төсөлд burst нь файлд өгөгдсөн тул тэр асуудал гараагүй. Convoy туршилт нь FCFS-ийн сул талыг тоогоор харуулсан: нэг урт task богино task-уудын хүлээлтийг 7 дахин өсгөсөн (6.0 → 43.6).

RR нь номын жишээ, `eight.txt`, `same_priority.txt` дээр хамгийн бага response time өгсөн бол эдгээрийн дундаж waiting time хамгийн их байлаа. Ойролцоо урттай task-ууд ээлжилж ажиллахад бүгд сүүлдээ дуусдаг учраас ийм үр дүн гарсан. Quantum-ын туршилт нь хоёр туйлыг баталсан: q их бол RR нь FCFS болно, q бага бол хариу хурдан ч context switch огцом өснө. Симуляторт context switch-ийн зардал 0 тул q = 1 үеийн бодит гүйцэтгэлийн уналтыг тооцоогүй.

`eight.txt`-ийн Priority хуваарьт priority 1-тэй T6 нь 160 нэгж хүлээж, хамгийн сүүлд ажилласан. Харин SJF дээр хамгийн эхэнд ажилласан. Шинэ өндөр priority-тэй task байнга ирдэг системд T6 хэзээ ч ажиллахгүй байж болох тул aging хэрэгтэй.

Хязгаарлалт: task-ыг slice дундуур нь preempt хийхгүй. Preemptive SJF ба Priority, aging, context switch-ийн зардал, I/O, олон CPU-г загварчлаагүй. Нэг удаад 1000 хүртэл task, нэг утга 10⁶ хүртэл байна. `__sync_fetch_and_add` зөвхөн GCC, Clang-д ажилладаг. UI ажиллуулахад Python сервер хэрэгтэй. Сервер асаагүй үед CLI-ийн `-j` гаралтыг файлаас ачаалж харах боломжтой. Таван алгоритмын давуу ба сул талыг хэдхэн жишээгээр харуулсан бөгөөд бүх ачаалалд аль нь хамгийн сайн гэж дүгнээгүй.
